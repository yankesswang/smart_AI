# 預測模型評估：為什麼閉環用 Ridge 而不是 TabFM

這份文件記錄一次實驗的完整過程與結論：把時序預測接進 Monitoring 閉環時，
TabFM 與 Ridge 誰適合。結論是**閉環用 Ridge、工作台用 TabFM**，理由不是效能，
而是 TabFM 在「剛開始劣化」這個唯一有價值的時間窗上會預測錯方向。

所有數字都是本機實測（RTX 4090 / 48 核 CPU），可用文末的重現步驟複驗。

## 1. 背景與目標

原本的預測模組只有一個入口 `/api/prediction/forecast`，由人在工作台主動查詢，
**不在閉環內**：`agents/` 與 `orchestrator.py` 都沒有呼叫 `ForecastService`。

目標是把預測接進既定流程，成為 Monitoring 的證據來源：在健康度還沒跌破告警線之前，
用外推提前示警。

判斷基準因此很明確——**只有在「尚未跌破門檻、但即將跌破」的那幾個 tick 內
給出正確預測，這個功能才有價值**。太晚預測到，門檻告警本來就會觸發。

## 2. 效能：TabFM 有多慢

### 2.1 成本拆解

一次 12 步遞迴預測（context 19 列 × 10 特徵）：

| 項目 | CPU | GPU (RTX 4090) | 備註 |
|---|---|---|---|
| 權重載入 | 7.6 s | 8.4 s | 每 process 一次 |
| `fit` | 0.03 s | — | in-context 模型，只是存下表格 |
| `predict` 單筆 | 600 ms | **44.7 ms** | 每次呼叫的固定開銷 |
| `predict` 12 筆 | 790 ms | 42.6 ms | 幾乎與單筆同時間 |
| **遞迴 12 步** | **7.7 s** | **0.50 s** | 12 次 `predict` |
| Ridge 同一工作 | **4 ms** | — | 手刻高斯消去 |

**關鍵觀察**：12 筆與 1 筆的耗時幾乎相同（42.6 ms vs 44.7 ms）。
成本由「呼叫次數」而非「資料量」決定——遞迴 12 步付了 12 次固定開銷。

### 2.2 批次化：可行但不該用

既然開銷來自呼叫次數，一次送 12 列可得約 10× 加速（7.7 s → 0.75 s）。
但遞迴預測本質上是循序的：每一步的預測要當作下一列的 lag 特徵。
批次化必須先「猜」出未來的特徵，實測兩種猜法都有問題：

| 猜法 | 結果 |
|---|---|
| 凍結特徵、只改 `tick` | 預測 90.6（真值約 84）——模型看不出時間推進，幾乎不動 |
| 用近期斜率線性外推特徵 | 方向對，但與遞迴版差距大 |

第二種猜法在五種序列形狀下與遞迴版的差距：

| 情境 | 遞迴 | 批次 | 差距 |
|---|---|---|---|
| flat healthy | 98.81 | 99.10 | 0.29 |
| plateau | 91.97 | 91.98 | 0.02 |
| steady decline | 80.24 | 83.00 | 2.76 |
| noisy decline | 85.00 | 82.86 | 4.20 |
| **sharp drop** | **77.43** | **71.01** | **6.53** |

平穩情境幾乎一致，但**急速劣化時差 6.5 分，剛好跨過 75 的告警門檻**——
遞迴說不告警、批次說告警。批次化不是更快的等價實作，是另一個更不可信的預測器，
且失準處正好是最需要準確的地方。**未採用。**

### 2.3 效能結論

GPU 把單次成本從不可行（7.7 s）降到可用（0.50 s），配合每 6 tick 才重算一次的
降頻策略，每 tick 攤提 0.087 s，測試時間從 144 s 降到 34 s。

**效能不是最終的否決原因**——GPU + 降頻已讓 TabFM 在閉環內跑得動。
真正的否決原因在下一節。

## 3. 正確性：TabFM 預測錯方向

### 3.1 端到端結果：trigger 一次都沒觸發

在 `bearing-degradation` 情境跑完整閉環，**預測 trigger 從未觸發**——
即使關閉降頻、每 tick 都預測，結果相同。

時間線（`M-A` 的自算健康度）：

| tick | health | 事件 |
|---|---|---|
| 7 | 88.66 | 累積滿 8 點，預測開始可用 |
| 8 | 84.09 | |
| **9** | **79.40** | **門檻 75 尚未跌破——唯一有價值的時間窗** |
| 10 | 73.25 | 跌破門檻，threshold 告警觸發 |
| 11 | 64.00 | |

預測可用到門檻跌破之間**只有 3 個 tick**。

### 3.2 決定性對照

在 tick 9（health 79.40）對同一份歷史，兩個模型的 12 步預測最低點：

| 視窗長度 | TabFM | Ridge |
|---|---|---|
| 最近 8 點 | 77.72 ✗ | **20.12 → 觸發** |
| 最近 9 點 | 77.92 ✗ | **15.01 → 觸發** |
| 最近 10 點 | 77.85 ✗ | **12.72 → 觸發** |
| 全序列 | 77.85 ✗ | **12.72 → 觸發** |

**TabFM 在任何視窗長度下都不觸發**（全部高於門檻 75），Ridge 全部觸發。
再往前一個 tick（tick 8，health 84.09），Ridge 仍觸發（21.13），TabFM 仍不動（82.28）。

### 3.3 完整軌跡

問題不是「預測得不夠低」，是**方向會反轉**：

```
context: [100, 100, 99, 97, 93, 88, 84, 79]     實際約 -5/tick
predict: [75.2, 72.4, 72.1, 74.4, 79.8, 83.6, 84.6, 83.9, 83.3, 84.4, 86.4, 88.3]
          └── 前 3 步正確下降 ──┘└──────── 觸底後一路回升 ────────┘
```

TabFM 預測這台機器會**自己好轉**。軸承劣化不會自己好轉。

### 3.4 滑動視窗：有幫助但不足

平坦前綴會加重回歸（見 §4.2），所以測試了截短 context。
方向正確——tick 10 時 win8 給 36.67，優於全序列的 56.85——
但在關鍵的 tick 9 仍不足以跨過門檻（77.72 vs 75）。**未採用。**

### 3.5 Ridge 的誤報檢查

預測式告警的主要風險是誤報。四種情境全部正確：

| 情境 | Ridge 預測低點 | 判定 |
|---|---|---|
| 健康平穩（含雜訊） | 98.62 | 不觸發 ✓ |
| 輕微波動未劣化 | 96.23 | 不觸發 ✓ |
| 短暫下探又回升 | 98.63 | 不觸發 ✓ |
| 真實劣化 | 32.94 | 觸發 ✓ |

## 4. 根因分析

測了四個假說，前兩個被推翻。

### 4.1 推翻：不是「數值超出訓練範圍」

TabFM 確實會外推到 context 最低值以下：

| context | 最低值 | 預測最低 | 跌破？ |
|---|---|---|---|
| 100→79 | 79.0 | 72.1 | 是 |
| 60→39 | 39.0 | 32.1 | 是 |
| 30→9 | 9.0 | 2.1 | 是 |

### 4.2 推翻：不是「訓練資料太少」

乾淨的等速下降，只改列數：

| 列數 | 真值 | TabFM | 誤差 |
|---|---|---|---|
| **8** | 60.0 | 60.5 | **+0.5** |
| 10 | 50.0 | 50.4 | +0.4 |
| 16 | 20.0 | 19.7 | −0.3 |

**8 列就已經很準**，而 8 列正是系統下限。列數不是問題。

真正相關的是**序列的形狀**。固定 10 列，只改平坦前綴的比例：

| 序列組成 | 收尾 | 預測走向 |
|---|---|---|
| 純下降（無平坦） | 55.0 | 50.4 → 13.5 正確 |
| 2 列平坦 + 8 列下降 | 60.0 | 55.5 → 23.9 正確 |
| **5 列平坦 + 5 列下降** | 75.0 | 74.5 → **80.1 回升** |
| **7 列平坦 + 3 列下降** | 85.0 | 85.6 → **89.3 回升** |

平坦佔一半以上時，TabFM 判定「常態是 100，最近下跌是偏離」，於是預測回歸常態。

### 4.3 推翻：不是「單步就不準」

拿掉遞迴、只問下一個值：context 尾端 79、實際斜率 −5/tick，
**單步預測 75.19，真值約 74**。單步幾乎正確。

### 4.4 成立：遞迴放大的均值回歸

三組不同數量級的序列，預測尾端都回到自己 context 平均的 82–96%：

| context | context 平均 | 預測尾端 | 佔平均比例 |
|---|---|---|---|
| 100→79 | 92.5 | 88.3 | 96% |
| 60→39 | 52.5 | 48.3 | 92% |
| 30→9 | 22.5 | 18.3 | 82% |

這個**尺度不變性**是均值回歸的特徵——若是數值範圍限制，低數值那組不會有同樣行為。

**機制**：TabFM 是 in-context 模型，從給定的表格學「這個序列的常態長什麼樣」。
訓練表 y 值為 `[100, 99, 97, 93, 88, 84, 79]`，多數落在 88~100，模型學到的常態偏高。

單步預測時，`lag_1=79` 與負的 `slope_3` 是強訊號，所以正確。
但遞迴時**每一步都把自己的預測餵回去當 lag 特徵**：走了 3 步後，
近期訊號被自己生成的值稀釋，學到的「常態 88~100」開始主導，於是往回拉。

這是遞迴預測的誤差累積，在 in-context 模型上特別明顯——它的先驗完全來自那張小表格。

### 4.5 為什麼 Ridge 反而對

Ridge 沒有「常態」的概念，只有一條直線，其強假設是**趨勢會持續**。
這恰好符合機台劣化的物理行為：軸承不會自己好轉。

TabFM 更聰明、會考慮回歸到常態，但**那個聰明在這裡是錯的先驗**。

而故障情境的本質是「機台先正常運轉一段時間，然後開始劣化」——
剛開始劣化的那幾個 tick（預測唯一有價值的時間窗）context 必然是
「大量平坦 + 少量下跌」，正是 TabFM 最會判斷錯的形狀。**這個錯誤幾乎必然發生。**

## 5. 結論與設計決定

### 5.1 閉環用 Ridge

`agents/monitoring.py: forecast_health()` 明確指定 `model="ridge"`：

* **正確**：在關鍵時間窗給出正確方向（§3.2），且四種情境無誤報（§3.5）
* **夠快**：4 ms，每 tick 都跑得起，不需降頻也不需 GPU
* **可重現**：確定性演算法，CI 與 Demo 行為一致

Ridge 在此不是「將就」——預測式告警的價值來自「每 tick 都在看未來」，
而非單次預測的絕對精度。

### 5.2 TabFM 保留給工作台

`/api/prediction/forecast` 維持 `auto`（TabFM 優先）。工作台是人工查詢、
context 可拉長、不做跨門檻的自動決策，是 in-context 模型合適的場景。

### 5.3 GPU 支援：環境變數，不進版控

`FACTORY_GUARDIAN_TABFM_DEVICE=cuda` 可啟用 GPU（預設 `cpu`）。

`pyproject.toml` 仍釘 CPU-only torch，**GPU 設定刻意不寫進專案依賴**：
CUDA wheel 約 2.5 GB，且沒有 GPU 的機器會退回 7.7 s／次，等於不可用。
由操作者自行安裝 CUDA build 後以環境變數開啟。

### 5.4 已知限制

預測 trigger 目前**不會提早觸發事件**。原因是 `fired` 去重機制：
tick 8–9 預測雖已成立，但其他 trigger 條件未達成、不構成事件；
等 tick 10 成立時門檻也同時跌破了。

現況是預測作為**額外證據**進入事件，讓下游看得到「照這樣下去會掉到 13」，
但不改變觸發時機。要取得實質的提早告警，需讓預測 trigger 能獨立構成事件
（如同現行的 trend trigger），這會影響 False Positive KPI，需另行評估。

## 6. 重現步驟

效能（GPU 需自行安裝 CUDA build 的 torch）：

```bash
FACTORY_GUARDIAN_TABFM_DEVICE=cuda python -c "
import time
from factory_guardian.prediction import ForecastService
s = ForecastService(); series = [100 - i*0.5 for i in range(20)]
s.forecast_series(series, horizon=12)                      # warm up
t = time.perf_counter(); s.forecast_series(series, horizon=12)
print(f'{time.perf_counter()-t:.3f}s')"
```

均值回歸（§4.4，不需 GPU）：

```bash
python -c "
from factory_guardian.prediction import ForecastService
s = ForecastService()
for seg in ([100,100,99,97,93,88,84,79], [60,60,59,57,53,48,44,39]):
    r = s.forecast_series(seg, horizon=12)
    print([round(v,1) for v in r['predicted']])"
```

關鍵時間窗對照（§3.2）：

```bash
python -c "
from factory_guardian.api.session import DemoSession
s = DemoSession(); s.reset('bearing-degradation')
for _ in range(40): s.tick()
h = s.orch.monitoring.health_history['M-A'][:10]      # tick 9, health 79.40
for m in ('auto', 'ridge'):
    r = s.prediction.forecast_series(h, horizon=12, model=m)
    print(m, round(min(r['predicted']), 2))"
```
