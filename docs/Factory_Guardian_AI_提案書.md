## 第 1 頁：問題與場域

一組對照組的產能達成率是本專案測到的所有結果裡最漂亮的一格：**99.0%**（實測，`hazard-zone` 情境，
`benchmark.json` Baseline A）。代價是它讓一名人員在**運轉中的機台旁邊站了 88 分鐘**（實測，
`hazard_exposure_min`）。這是本提案要處理的核心矛盾：多數工廠把「產能」與「安全」當成互斥的旋鈕，
而現行的偵測性投資（更多感測器、更靈敏的門檻）解決不了這個矛盾——它只能解決「有沒有看到異常」，
解決不了「看到之後，系統敢不敢在還沒確定答案時，選擇犧牲一點產能去保護人」。

**場域收斂**：一座中大型製造廠、一條產線（M-A 主要加工機 → M-B 替代加工機 → M-C 後段包裝機）、
三種設備故障（軸承劣化、冷卻失效、馬達過載）與一種工安事故（人員誤入運轉中危險區）。
每一種故障若未被及時接住，實測會走到**二次損壞**（軸承劣化 210,000 NTD、冷卻失效 150,000 NTD、
馬達過載 260,000 NTD，**實測**，`twin/faults.py`）；工安事故的期望代價則取決於一個本專案**沒有**
任何公開統計可引用的假設參數（曝露致傷機率 0.5%/小時，**假設**，見第 12 頁）。
本提案的立場很直接：**產能與工安不是同一把尺上的兩端，工安是硬限制。**

## 第 2 頁：現行流程

多數工廠的異常處置在告警之後就斷了。本專案把這段空白具體建成 Benchmark 的第三組對照組
**Baseline C（現行流程）**：固定門檻偵測（無攝影機、只認 CRITICAL 瞬時讀值）→ 告警 →
**人工判定根因 90 分鐘**（到場 15 ＋現場量測 30 ＋查手冊與歷史工單 30 ＋與生產確認 15，**假設**，
判定期間機台照跑照劣化）→ 停機維修 → 復機，**不轉單**。這 90 分鐘不是我們編的悲觀值：
**實測結果是，三個設備故障情境裡這個判定流程一次都沒有跑完**——平均在第 40 分鐘就被故障自己
揭曉打斷（軸承咬死、馬達燒毀，機台自己停下來）。人工判定的價值在這裡是負的。

第二個痛點是**工單完整度只有 60%**（**假設**，依 `WorkOrder.completeness()` 欄位口徑：
有故障描述與機台，但缺手冊條款、建議零件、SOP 連結）。第三個是知識問題：維修判斷分散在少數
資深技師身上，沒有結構化，換班或退休就把判斷依據帶走了。工安控制則是**程序性**的（SOP、圍籬、
教育訓練、定期巡檢），不是**偵測性**的——沒有一雙一直盯著危險區的眼睛，這正是第 1 頁那 88 分鐘
會發生的根本原因。

## 第 3 頁：產品總覽

**一句話定位**：當設備、產線或工安異常發生時，AI 不只警告，而是自動走完
**偵測 → 診斷 → 影響分析 → 方案規劃 → 安全檢查 → 人工核准 → 執行/派工 → 驗證恢復**
八階段閉環，並在執行後回到模擬器重新量測結果，而不是停在「LLM 建議」。

**三個設計理念**：(1) 規劃跑在**診斷信念模型**上，不是跑在答案上——`fork_as_belief()`
拿掉真實故障標籤，換上 Diagnosis Agent 自己推論出來的故障，診斷錯了投影就會錯，
由 Verification Agent 在真實孿生體上抓出來；(2) 排名用**固定尺規**加權（`optimizer.py`），
不用 min–max 正規化，並在排名後再跑一次**權重穩健性掃描**，回答「權重是你自己訂的，換一組會不會
換人」；(3) Safety 是**硬限制**，具否決權，而且看的是「方案會把設備帶到哪裡」，不只是現在的數值。

**特色**：多模態證據（溫度／振動／電流／轉速＋現場影像＋手冊／SOP／歷史工單）、
可稽核（每個判斷附時間點、來源、信心分數，落選候選也攤開）、人工在環（高風險動作需核准）、
閉環驗證（執行真的改變孿生體狀態）。**明確不做**：不直接控制真實 PLC/CNC、
不宣稱故障模型可泛化所有設備、不做完整 MES/SCADA、**不以 LLM 直接下控制指令**。

## 第 4 頁：使用者與買方

| 角色 | 對象 | 情境 |
|---|---|---|
| **使用者** | 設備維護技師、產線班長 | 領工單、看診斷證據、執行維修、確認驗證結果 |
| **決策者** | 廠務／設備維護主管、工安主管 | 核准高風險動作（停機、修改控制狀態）、審視 Safety 裁決 |
| **採購者** | 數位轉型辦公室或 IT／OT 團隊 | 預算多掛在「智慧製造」或「工安改善」項下 |

**目標客戶**（**假設**，商業判斷）：有高價旋轉設備、停機成本高、維修知識分散在少數老師傅身上的
中大型製造廠（電子組裝、精密加工、化工、食品）。

**使用情境**：值班人員在戰情 Dashboard 上看到 KPI 反白示警；點開步驟卡看到「異常從哪裡來、
系統怎麼算出信心度、為什麼不是別的答案」；主管在核准對話框上簽名放行停機或轉單；
技師領到含零件清單、SOP 連結與預估工時的工單；工安主管在 CAM-01 監視畫面上看到
Safety Agent 用哪一條規則、哪一組讀值，裁決「有人在危險區」。每一步都能點回它的來源證據，
不是黑盒子的一句「建議停機」。

## 第 5 頁：系統架構

```
Detect ──▶ Diagnose ──▶ Impact ──▶ Plan ──▶ Safety ──▶ Approve ──▶ Execute ──▶ Verify
Monitoring  Diagnosis   Production  Production  Safety   Policy    Simulator  Verification
  Agent       Agent       Agent       Agent      Agent    Engine      API        Agent
                    Factory Digital Twin（唯一知道真相的地方）
```

| 層 | 元件 | 部署位置（**實測不變式**） |
|---|---|---|
| Data | Digital Twin（拓撲／故障模型／模擬引擎／干擾與現實落差） | EDGE |
| Knowledge | Manual／SOP／維修紀錄 ＋ CJK-aware TF-IDF 檢索 | EDGE |
| Agent | 六個 Agent（Monitoring／Diagnosis／Production／Safety／Maintenance／Verification）＋ VLM 後端 | EDGE |
| Governance | Safety 硬規則、Policy Engine、人工核准、JSONL 稽核 | EDGE |
| Decision | 加權多準則排名 ＋ 權重穩健性掃描（**非 LLM**） | EDGE |
| Action | Simulator API／Dashboard／CLI | EDGE／CLOUD 混合 |

**控制關鍵路徑上的每一個元件都必須是 EDGE**——這是 `deployment/tiers.py` 宣告、由測試
`critical_path_is_edge_only()` 守住的不變式（實測：`True`）。只有 LLM 敘述、雲端知識庫、事件報告
放在 CLOUD，且斷網時全部**降級**而非失效（第 13 頁展開）。

## 第 6 頁：異常偵測

Monitoring Agent 用**門檻 ＋ 趨勢 ＋ 健康度**三重觸發，並加了兩道抗雜訊機制：
**N-of-M 門檻確認**（越界須在最近 3 個取樣裡出現 2 次，代價是真實故障偵測晚至多 1 個 tick）與
**動設備前觀察窗**（6 個 tick，用於分辨「新穩態」與「才剛開始的劣化」）。2026-09-06 新增
**TTT（到達門檻剩餘時間）預測**：只讀 Agent 自己可觀測的歷史（不讀故障標籤），優先用時序模型
換算成分鐘，拿不到結果退回線性外推；TTT 進了 `failure_risk` 但只是加權項（最多 +0.35），
不會蓋過已經量到的健康度與趨勢。

**實測結果**（設備故障 3 情境平均，`benchmark.json`）：偵測延遲 Guardian **4.7 min** vs
現行流程 **7.3 min**。**誤報情境**（4 個 Ground Truth 為空的干擾）：Guardian 只有 **2/4**
情境真的觸發告警事件（現行流程 4/4 都觸發），其中一格是**主動棄權**（健康度與趨勢顯示已停在新
穩態，只告警、不動設備）；但觸發的另一格 `fp-warm-up` 裡 Guardian 仍實際誤動作 **3 次**
（轉單＋停機＋維修，現行流程則是派出技師 4 趟）——溫度連續 8 分鐘超過危險門檻且持續上升，
當下與早期冷卻失效沒有可觀測差別，這是我們選擇 6 分鐘觀察窗必須付的誠實代價，不是被藏起來的失敗。

## 第 7 頁：根因與證據

診斷排名由**感測器指紋餘弦相似度（權重 0.75）**主導，加上**歷史先驗（0.15）**與
**文件支持度（0.10）**，RAG 只負責產生可引用的 Evidence，不決定答案；信心度會被訊號強度壓抑，
不足時系統選擇繼續觀察。**實測**：初次診斷正確率 **83.3%**（5/6，偵測當下第一次比對），
確認、必要時重規劃之後 **100%**——那 16.7 個百分點是觀察窗與重試機制買到的，不是憑空冒出來的。

2026-09-06 新增**多原型指紋**：單一質心無法表示雙側故障（例如馬達失載 vs 過載），
`motor_overload` 與 `cooling_failure` 各補了一個手冊來源的第二原型，`bearing_degradation`
只有一個方向不受影響。外部資料（AI4I）上重跑：Top-1 從 0.724 升到 **0.821**（詳見第 10 頁）。
另建有**判別式接手層**（`DiscriminativeReranker`），在同機台帶讀值的標註案例 ≥ 8 筆時參與合分
（M-A 19 筆、M-B 8 筆可啟用，M-C 3 筆仍是冷啟動）——**預設權重為 0、不掛載**，因為 Demo 的維修歷史
是我們自己寫的合成語料，用它推動排名等於用自己編的資料證明自己。這條路徑留給真實標註歷史的場域。

## 第 8 頁：安全治理

Safety Agent 具**否決權**，除了現況規則還有**預測型規則**（SR-02P／SR-03P／SR-13）：
拿方案乾跑出來的訊號峰值判斷，而不只看當下數值。**實測範例**：PLAN-A（維持全速）被 BLOCK，
裁決原文——模擬顯示本方案會讓 M-A 振動由目前 **5.65 mm/s** 升至 **14.18 mm/s**，超過危險門檻
**7 mm/s**；在振動持續上升的情況下維持產出，等同於為了產量接受旋轉件破損風險。被擋下的方案不會
消失，會以紅底刪除線保留並列出理由。2026-09-06 新增**方案參數搜尋**：PLAN-C／PLAN-D 的
「延後停機」變體（先讓機台把手上這批做完）會用延後窗內的預測峰值再過一次 SR-02P／SR-03P——
**延後越久越容易被預測型規則擋下**；即使沒被擋，執行層目前也沒有「N 分鐘後再停機」這個動作，
因此延後變體只留作對照分數，不會被選為家族代表。

**人工在環**：停機、修改控制狀態等高風險動作必須人工核准；Safety Override 為系統禁止動作。
**可稽核**：每次閉環寫入 JSONL，實測**27 筆／21,575 bytes**（`deployment/budget.py`）。
**工安是硬限制，不是加權項**——`hazard-zone` 情境 Guardian 用 25% 產能換掉 87 分鐘曝露
（99.0%→74.3%；88 min→1 min，**實測**），我們不會為了讓 ROI 好看而調整這個立場（第 12 頁展開）。

## 第 9 頁：介面與 UX

Dashboard 走 **Tactical Telemetry（暗色 CRT 終端）**風格：單一 hazard red 強調色分級狀態、
terminal green 只保留給「VERIFIED」鋼印、無圓角無陰影無漸層、系統字體堆疊（不依賴競賽現場網路）。
2D 產線圖有兩種視圖：**ARCADE**（像素風格即時模擬，機台冒煙噴火花、技師進場、危險區有人闖入會
跳驚嘆號）與 **SCHEMATIC**（黑紅戰情示意圖，供列印與截圖）。

**六格步驟卡可展開推理**：每一步看得到「看到什麼 → 怎麼算 → 為什麼不是別的 → 結論」。
診斷格把信心度拆成算式（指紋餘弦 × 0.75 ＋ 歷史先驗 × 0.15 ＋ 文件支持 × 0.10，判別式接手層啟用時
再加一列），並列出落選候選的餘弦值；方案格拆出六準則加權貢獻；工安格逐條列出 `SR-xx` 規則與擋下
理由。**CAM-01 工安監視畫面**刻意不放實景照片（照片是死的，人員離開後畫面不會變），每一格都綁在
`CameraObservation` 的欄位上。**`/benchmark` 對照組報告頁每次載入都真的重跑**（11 情境 × 4 模式），
不是快取也不是預錄。

## 第 10 頁：Demo 與驗證

**決賽 12 分鐘閉環劇本**（`factory-guardian stage`，8 段、4 分鐘）：正常 → 異常注入 → 偵測 →
確認觀察 → 診斷 → 影響 → 規劃 → Safety → 核准 → 執行 → 驗證。連續 30 次執行**成功率 100%、
決策指紋完全一致**（`stage-check --runs 30`），斷網模式（`--offline`）指紋與有網路時**逐位元相同**。
全套 **986 個測試**，離線約 42 秒跑完。

**三條外部資料驗證線**，誠實寫出輸的地方：

| 資料集 | 性質 | 結果 | 輸的地方 |
|---|---|---|---|
| AI4I 2020（合成，CC BY 4.0） | 根因歸因 | 單原型 Top-1 **0.724**→多原型 **0.821** | 仍輸 LogisticRegression **0.964** |
| DCASE2020 pump（真實工業錄音） | 聲學偵測 | 平均 AUC **0.903** vs 官方 baseline 0.726 | — |
| CWRU（真實加速規量測） | 軸承振動診斷 | 內圈/滾珠/外圈 Top-1 **0.994** | 偵測任務單一 RMS 門檻 AUC **1.000** 贏過指紋 **0.982**；跨嚴重度轉移 Top-1 **0.335 ＝ 隨機** |

CWRU 的跨嚴重度結果尤其重要：拿「壞得明顯」訓練、測「剛開始壞」，指紋法完全失效——
**本專案不宣稱已驗證早期偵測能力**，這是誠實邊界，不是行銷語言可以繞過的地方。

## 第 11 頁：量化成果

**量化成果一律以 Guardian 對 Baseline C（現行流程）為主要對照**，A／B 只是兩個理論極端
（見第 2 頁）。以下為設備故障 3 情境平均，**實測**（`benchmark.json`）：

| KPI | Baseline C（現行流程） | **Factory Guardian** |
|---|---:|---:|
| 偵測延遲 | 7.3 min | **4.7 min** |
| 診斷確認（MTTD） | 40.0 min | **10.7 min** |
| 產能達成率 | 54.2% | **94.6%** |
| 最大交期延遲 | 24.5 min | **0 min** |
| 二次損壞 | **發生** | 未發生 |

**誠實的代價要主動講**：初次診斷正確率只有 **83.3%**（5/6），確認之後才到 100%；
Guardian 的 10.7 分鐘 MTTD 裡有 6 分鐘是刻意的觀察窗——關掉它 MTTD 回到 5.0 分鐘、
產能回到 96.9%，但那 2.3 個百分點買到的是可分辨誤報與更正錯誤初診。誤報情境裡
`fp-warm-up` 一格 Guardian 誤動作 3 次（轉單＋停機＋維修），我們不打算辯護。工安情境
Guardian 用 25% 產能換 87 分鐘曝露（99.0%→74.3%）。**目前沒有任何情境走到「驗證失敗→重新規劃」**
——重試路徑有獨立測試守著，但 Benchmark 上的重規劃次數目前是 0，我們不會寫成已經發生的事。

## 第 12 頁：商業模式

| 項目 | 內容 |
|---|---|
| 收費方式 | 平台 SaaS（廠／線／機台）＋ AI Usage（Camera／Agent／Inference）＋ System Integration（一次性）＋ Managed Service |
| 通路 | 中華電信整合 5G 專網、MEC、hicloud、OT 資安與維運服務 |

**基準情境（全廠 6 線，逃逸率 25% 機率混合，**假設**）**：年度效益 **4,564,752 NTD**、
第一年 ROI **+64.5%**、穩態年度 ROI **+172.5%**、簡單回收期 **4.6 個月**（**推導**，
`business.json`）。效益 69.8% 來自「避免二次損壞」——這代表商業案例的重心是**把那 25% 沒被接住、
最後演變成主軸損傷的事件攔下來**，不是省一點電、快一點修。

**主動寫出不成立的條件**：保守情境（假設現況從不讓劣化走到二次損壞）穩態 ROI **−83.8%**，
不會回本；單線試點穩態 ROI **−17.6%**，廠級固定成本（5G 專網＋MEC）需**至少 2 條產線**攤平；
現況告警逃逸率需 **≥ 5.3%** 本方案才在財務上成立。**如果貴廠的告警從不漏接，這方案不值得買。**

**競品比較**（同一評審體系歷屆得獎作品，研究文件 §2、§4.5）：

| 作品 | 重疊 | 我們的差異 |
|---|---|---|
| AI 智慧刀把（2024 社會組季軍） | 振動訊號預測磨耗 | 振動只是四訊號之一；輸出是**帶證據的根因排名**，不是壽命曲線 |
| 數位孿生 AI 檢測（2022 亞軍） | 虛實同步、遠端機台 | 孿生體是**驗證機制**（信念模型乾跑＋執行後驗證），不是視覺化展示 |
| 無所遁形（2025 社會組季軍） | 不中斷偵測異常 | 差別在偵測之後：根因→影響→方案→Safety→核准→工單→修復驗證 |

三件作品都停在「偵測／預測」，我們的差異軸是把偵測之後的六個步驟做完並量測。

## 第 13 頁：中華電信合作

**本作品不宣稱與中華電信有既有合作關係**；以下為需求側工程數字，實際頻譜、涵蓋與細胞容量
需由中華電信 RF 規劃確認。

**5G 專網**（**假設規模**，Pilot Line：3 台機台各 1 路危險區 + 1 路產線總覽 = **4 路攝影機**）：
總上行頻寬需求 **16.19 Mbps**（工安影像 16.17 ＋ 感測遙測 0.016，**推導**，`deployment/budget.py`）。
Wi-Fi 不適用的理由：上行無排程保證、無法對單一流做 QoS、金屬環境換手掉包、隔離只能靠上層 VLAN。

**MEC 邊緣運算**：邊緣前處理把 2 台 CNC 三軸 10kHz 原始振動波形（0.96 Mbps）壓成 11.5 kbps
特徵串流，縮減 **83.3 倍**；影像若送雲端判讀需 5.24 TB/月，邊緣判讀後只送事件與匯總僅
22.9 MB/月，縮減 **228,916 倍**——這是 MEC 最直接的經濟理由，也是原始波形不出廠的資安理由。
**斷網續跑**：`critical_path_is_edge_only()` 不變式（實測 `True`，測試守住）保證 Detect→Diagnose→
Safety→Approve→Execute→Verify 全部在 EDGE；斷網時僅 LLM 敘述降級為邊緣確定性敘述器，
**決策指紋斷網前後逐位元相同**（Demo 已驗證）。Safety 決策延遲目標 **250 ms**，
邊緣可用度目標 **99.9%**（`SAFETY_LATENCY_TARGET_MS`／`SEGMENT_AVAILABILITY`，設計假設）。

**中華電信可辨識收入**（單一 6 線客戶）：5G 專網 28,000/月 ＋ MEC 代管 18,000/月 ＋ 邊緣硬體
450,000 一次性 ＝ 年度 552,000 ＋一次性 450,000；若 System Integration 與 Managed Service
亦由中華電信承接，單一客戶年度合約規模約 **1.0–1.7 百萬 NTD**（**假設**，未經報價驗證）。

## 第 14 頁：永續與風險

**永續**（設備故障 3 情境平均，**實測**）：單位產出能耗 Guardian **0.33 kWh/件**，比現行流程
0.63 低 48%，比固定門檻告警 0.75 低 56%。年度換算（全廠 6 線基準情境）：避免浪費電力 42.6 kWh、
避免碳排 20.9 kgCO2e、減少人員危險曝露 104.4 分鐘。**誠實揭露**：碳費效益一年僅 6 NTD，
對 ROI 沒有實質影響，價值在 ESG 揭露與碳盤查，不在財務回收。

**風險與回答策略**：

| 風險 | 回應 |
|---|---|
| 資料是假的嗎 | Sensor/Orders/History 明確標示 synthetic；事件、Agent 決策、KPI 驗證都是真實執行，稽核軌跡可現場調閱 |
| 診斷法可信嗎 | 外部資料上輸給 LogisticRegression（0.821 vs 0.964）；已規劃判別式接手層供真實標註歷史場域啟用 |
| 早期偵測宣稱 | CWRU 跨嚴重度轉移 Top-1 ＝ 隨機——**不宣稱**已驗證早期偵測能力 |
| TabFM 授權 | 官方預訓練權重為非商業授權，正式商用需替換自有 checkpoint，API 與前端不需改動 |
| 舊作限制 | 2022–2025 得獎作品不得參賽；持續與歷屆得獎作品做差異化比較（第 12 頁） |
| 資安 | OT/IT 隔離下推至 5G 專網承載層；控制關鍵路徑不變式由測試守住 |

## 第 15 頁：團隊與路線圖

**本作品為社會組單人參賽**（官方規則允許 1–6 人）。**已完成**：Factory Digital Twin 與八階段
Agent 閉環、四組對照組 Benchmark（11 情境）、權重穩健性掃描與方案參數搜尋、TTT 預測、
三條外部資料驗證（AI4I／DCASE／CWRU）、商業案例三情境敏感度與破口分析、Dashboard 與稽核軌跡、
986 個測試。**誠實列出未完成的事**：現場訪談（5–10 位維修／工安人員）尚未進行；
CAM-01 目前是**腳本化合成觀測**，真實影像 VLM 尚未串接；P2 Bonus 的桌上型 Mini Machine
（ESP32＋小馬達＋溫振感測器）尚未建置。

**導入路線圖**：競賽 MVP（Simulator + Synthetic MES，現況）→ PoC 工廠（真實 OPC-UA/MQTT
感測器 + 歷史維修資料，微調工具與模型）→ Pilot Line（MES/SCADA/CMMS + 權限與 Safety Review，
**至少 2 條產線起跳**，見第 12 頁破口分析）→ Production（多產線、多設備商、HA/SOC/SLA，
擴充但不改核心閉環）。替換點都是明確介面：`FactoryTwin`（→ OPC-UA/MQTT Adapter）、
`VisionBackend`（→ 真實 VLM）、`KnowledgeBase`（→ 向量資料庫）。

**需要中華電信的合作**：一個願意做 Pilot 的產線場域、5G 專網與 MEC 節點的實測環境、
以及協助引介 2–3 位設備維護／工安主管完成本提案尚未做的訪談。
