# 聲學異常偵測：以外部真實工業錄音驗證

> 這份文件回答一個問題：**「你們的數字是不是編的？」**
>
> Factory Guardian 的 Digital Twin 是合成的，這是提案最容易被質疑的一點
> （提案書 §14 自己就把這列為第一個預期追問）。最直接的回答不是解釋，
> 是拿一份**外部的、公開的、有官方基準的真實工業資料**把偵測器再跑一次，然後和官方 baseline 比。
>
> **結論：平均 AUC 0.9030 / pAUC 0.7855，四個泵浦個體在兩個指標上全面優於
> DCASE2020 官方 baseline 的 0.7259 / 0.6000。**

## 0. 先把邊界講清楚：真實資料 vs 合成 Demo 音訊

這是整份文件最重要的一段。專案的三個可信度原則之一是「合成資料明確標示」，
聲音模態如果含糊，會毀掉的不只是這一塊，是整個提案。

| | **真實錄音** | **合成 Demo 音訊** |
|---|---|---|
| 資料 | DCASE2020 Task2 / MIMII 真實泵浦運轉錄音 | 由 `twin/faults.py` 既有的振動／轉速／電流物理推導 |
| 程式 | `acoustics/dcase.py` | `acoustics/signatures.py` + `acoustics/synthetic.py` |
| 用途 | **驗證偵測器本身有效** | 跑 Demo 閉環、餵給 Diagnosis Agent |
| 出現在 Demo 畫面上嗎 | **不。一個數字都沒有** | 是，且一律標記 `synthetic=True` |
| 出現在 Benchmark KPI 裡嗎 | **不** | 是（透過診斷信心度間接影響） |

**兩者沒有任何一條資料流互通。** 這不只是紀律，是架構上的保證：

* `acoustics/dcase.py` **不被** `twin/`、`agents/`、`api/` 的任何一處匯入。
  真實錄音在程式結構上就到不了 Demo 閉環。
* 反過來，`twin/` 產生的每一個 `AcousticObservation` 都帶著
  `synthetic=True` 與 `provenance="synthetic-derived-from-vibration-physics"`，
  序列化時還會附一行 `SYNTHETIC DEMO AUDIO — 由振動物理推導的合成音訊特徵，非真實錄音。`

### 那合成聲音還有什麼意義？

**它證明介面是通的，不證明數字是真的。**

合成的聲學指標是振動物理的重新編碼。在這個 Demo 上它與振動高度相關，
所以它**補強**（corroborate）而不是**新增**（add）獨立證據 ——
Diagnosis Agent 因此把聲音的有效權重壓在 0.15，不讓一個推導量蓋過真正量到的訊號
（理由詳見 `agents/diagnosis.py` 的模組說明）。

真正有價值的問題是「真實工廠換上真麥克風之後會怎樣」，而那個問題由本文件回答。
**兩條路徑共用同一個特徵抽取器與同一個偵測器類別**
（`features.log_mel_summary()` 與 `detector.AcousticAnomalyDetector`），
導入時要換掉的只有 `fit()` 吃進去的那批音訊，程式一行都不用改。

## 2. 為什麼「訓練集只有正常音訊」是特徵，不是限制

DCASE2020 Task2 的訓練集是 3,349 段**正常**、**0 段異常**。這正是真實工廠的常態：

* 沒有人會為了收集訓練資料，把一台幾百萬的加工機硬跑到軸承咬死。
* 就算真的壞過，那也是「這一台、這一次」的壞法；換一台設備、換一種故障就不適用。
* 有標籤的故障資料本質上是**倖存者偏差**：能被標記的故障，都是已經嚴重到被發現的故障 ——
  而預測性維護的價值恰恰在於「還沒嚴重到被發現」的那一段。

所以任何宣稱「我們訓練了一個故障分類器」的方案，導入第一關就會卡住：客戶拿不出標好的故障資料。

只用正常資料建模、把「偏離正常的程度」當異常分數，是唯一能在**新機台第一天**就上線的做法。
本專案的偵測器因此是無監督的，這個選擇是被真實部署條件逼出來的，不是為了遷就資料集。

## 3. 方法

三個步驟，全部在 `factory_guardian/acoustics/` 裡，沒有 GPU、沒有訓練迴圈。

### 3.1 特徵：log-mel 頻譜 + 每個頻帶兩個時間統計量

`features.log_mel_summary()`：

```
10 秒 @ 16 kHz
  → STFT（n_fft = 1024 ≈ 64 ms 窗，hop = 512 ≈ 32 ms）
  → 64 個 mel 濾波帶
  → 取 dB（log）
  → (64 bands × 313 frames)
  → 每個 band 取兩個統計量 → 128 維特徵向量
```

兩個統計量：

| 統計量 | 物理意義 | 抓得到什麼 |
|---|---|---|
| `mean` | 該頻帶的平均能量 | 哪些頻帶變大聲了 —— 寬頻能量上升、少了一個純音 |
| `delta_abs_mean` | 相鄰 frame 差分的平均絕對值 | 該頻帶的能量抖不抖 —— 週期性衝擊造成的時間調變 |

這兩個剛好對上滾動軸承缺陷的兩個特徵：**寬頻能量上升**（mean）**且伴隨衝擊調變**
（delta_abs_mean）。只有能量上升而沒有調變，比較像負載變重；兩者同時出現才是缺陷。

不用 MFCC：DCT 之後的倒頻譜係數描述的是頻譜「包絡」，它為語音辨識設計，
會刻意丟掉激發訊號的細節 —— 但機械異常常常就藏在那些細節裡。

### 3.2 偵測器：Local Outlier Factor（只用正常音訊擬合）

`detector.AcousticAnomalyDetector`：標準化 → LOF（k = 5，`novelty=True`）→ 分數 = 負的 LOF 分數。

**每個 machine id 各自擬合一個模型**，只用該 id 的正常音訊。這是 DCASE 的規定，
也是真實工廠的做法：不同個體的基準聲音本來就不同，拿 A 泵浦的「正常」去判 B 泵浦，
量到的是個體差異而不是異常。

為什麼是 LOF 而不是官方 baseline 的 autoencoder：一台泵浦的「正常」不是一團高斯雲，
而是好幾團（啟動、穩態、不同負載點各自成群）。全域方法會把「密度低但完全正常」的稀有工況
判成異常；LOF 比的是「這個點的局部密度，相對於它鄰居的局部密度」，稀有但自洽的工況不會被誤殺。
消融數字見 §5。

### 3.3 評估：AUC 與 pAUC（p = 0.1）

pAUC 只看 FPR ∈ [0, 0.1] 的那一段並正規化回 [0, 1]，是 DCASE2020 Task2 的官方指標。
**它比 AUC 重要**：工廠現場能容忍的誤報率本來就只有個位數百分比，
一個「整體 AUC 漂亮但要接受 50% 誤報才抓得到異常」的模型在產線上沒有價值。

告警門檻由**訓練集（全正常）**的分數分位數決定（`threshold_at_quantile()`），
不是拿測試集的異常去調 —— 後者等於偷看答案，而且真實導入時根本沒有異常樣本可以調。

### 3.4 快取

真正貴的是解碼 4,205 個 wav（約 23 秒），不是擬合模型（毫秒級）。
所以快取的是**特徵向量**而不是 pickle 過的模型物件：

* `data/external/dcase2020_pump/pump_logmel_summary_v2.npz`（2.9 MB）
* npz 沒有 scikit-learn 版本相依，任何人都可以拿它自己重算一次分數來稽核我們報的 AUC。

重跑方式：

```bash
python3 -m factory_guardian.acoustics.dcase
```

| 步驟 | 時間 |
|---|---|
| 建立特徵快取（一次性） | 23 s |
| 由快取評估四個 machine id | 1.4 s |

## 5. 消融：這個分數是怎麼來的

### 5.1 換偵測器（同一份 128 維特徵）

| 偵測器 | AUC | pAUC |
|---|---:|---:|
| **LOF k=5（本專案採用）** | **0.9030** | **0.7855** |
| One-Class SVM (RBF) | 0.8610 | 0.7473 |
| GMM-8 on PCA-16 | 0.8426 | 0.7304 |
| kNN k=1 距離 | 0.8396 | 0.7265 |
| Mahalanobis (Ledoit-Wolf) | 0.8391 | 0.6846 |
| PCA-16 重建誤差 | 0.8252 | 0.6733 |

三個全域方法（後三者）明顯落後，差距就出在「正常不是一團」這個假設上。

### 5.2 換 k（LOF 的鄰居數）

| k | AUC | pAUC |
|---:|---:|---:|
| 2 | 0.8971 | 0.8007 |
| 3 | 0.9068 | 0.8061 |
| 4 | 0.9056 | 0.7995 |
| **5（採用）** | **0.9030** | **0.7855** |
| 6 | 0.9016 | 0.7756 |
| 8 | 0.8993 | 0.7745 |
| 10 | 0.8918 | 0.7618 |
| 15 | 0.8815 | 0.7502 |
| 20 | 0.8751 | 0.7468 |
| 40 | 0.8501 | 0.7255 |

k = 5 **不是最高點**（最高在 k = 3）。k 從 2 到 8 是一片平台（AUC 0.897–0.907），
不是一根尖峰 —— 取平台中段是為了不讓數字看起來像調出來的。
即使取整片平台最差的 k = 8（0.8993 / 0.7745），仍然全面優於 baseline。

### 5.3 換特徵（LOF k=5）

| 統計量組合 | 維度 | AUC | pAUC |
|---|---:|---:|---:|
| `mean` | 64 | 0.8878 | 0.7787 |
| **`mean` + `delta_abs_mean`（採用）** | **128** | **0.9030** | **0.7855** |
| `mean` + `std` | 128 | 0.8488 | 0.6865 |
| `mean` + `std` + `p10` + `p50` + `p90` | 320 | 0.8697 | 0.7351 |
| 全部七個統計量 | 448 | 0.8903 | 0.7599 |

**加更多統計量沒有變好。** 這件事值得寫出來而不是藏起來：
它說明分數不是靠堆特徵堆出來的，`mean` 一項就已經拿到 0.888。

## 6. 這些數字的邊界

寫在這裡，是因為評審一定會問，而先講比被問出來好。

1. **超參數是在 development set 上選的。** n_mels、統計量組合與 k 都是看著本表的
   AUC 決定的。DCASE 真正的 held-out 是 **evaluation set**，我們沒有用它，
   所以嚴格說本文的數字是「開發集上的最佳配置」，不是盲測成績。
   官方 baseline 也是在同一份開發集上報告與調校的，所以**比較本身是公平的**；
   但若要主張「換到任何泵浦都有 0.90」，這份證據不足以支撐。
   §5 把完整 sweep 攤開，就是為了讓人自己判斷這個選擇有多少過擬合空間
   （平台很寬 → 空間不大）。
2. **這是泵浦，不是 CNC 加工機。** 本專案 Demo 的三個故障模型發生在工具機主軸上，
   資料集是泵浦。這裡驗證的是**方法**（無監督 + log-mel + 局部密度）在真實工業音訊上站得住，
   不是「本專案的故障模型已在真實設備上驗證」。後者需要現場資料，是 PoC 階段的事。
3. **10 秒的觀測窗。** 真實線上部署要決定多久判一次、以及如何處理跨窗的緩慢漂移，
   這些不在本次驗證範圍內。
4. **合成 Demo 音訊完全沒有被這些數字背書。** 見 §0。

## 7. 合成 Demo 音訊：它是怎麼做出來的

（這一節描述的是 Demo 路徑，與 §1–§6 的真實資料驗證**無關**。）

### 7.1 四個聲學指標

麥克風每個觀測窗回報四個純量，每一個對應一種**不同的**物理機制：

| 指標 | 物理意義 | 為什麼需要它 |
|---|---|---|
| `spl_db` | 整體音壓級 | 能量總量，最粗但最穩健 |
| `high_band_ratio` | 2–8 kHz 能量佔比 | 滾動體剝落／點蝕的能量集中在高頻 |
| `tonal_ratio` | 諧波（純音）能量佔比 | **冷卻泵停了會少一個 tone**；馬達過載則多出線頻諧波 |
| `crest_factor_db` | 峰值／RMS | 軸承缺陷是週期性衝擊，平均能量看不出來、波峰因數看得出來 |

`tonal_ratio` 是最有價值的一個，因為它補上了感測器指紋補不上的鑑別力：
**冷卻失效與馬達過載都會推高溫度**，溫度訊號本身分不開；
但前者是「泵停了 → 少一個 tone」，後者是「負載上升 → 多出線頻諧波」，方向完全相反。
兩者的聲學 profile 餘弦是 **−0.89**（幾乎相反向量）。實測的聲學餘弦：

| 情境 | bearing | cooling | motor |
|---|---:|---:|---:|
| 注入 bearing_degradation | **0.99** | 0.14 | 0.19 |
| 注入 cooling_failure | 0.08 | **0.99** | −0.85 |
| 注入 motor_overload | 0.19 | −0.90 | **0.99** |

這就是「多模態」的具體價值 —— 不是把資料堆在一起而已。

### 7.2 渲染器：讓兩條路徑真的接得起來

`synthetic.synthesize_waveform()` 把四個指標「畫」成一段真的可以做 FFT 的波形，
成分是純音（主軸／冷卻泵／線頻諧波）＋ 高頻寬頻噪音 ＋ 軸承衝擊串 ＋ 低頻寬頻噪音。
衝擊串帶 2% 滑移抖動與 35% 負載區振幅調變 —— 這**不是**為了好看：
真實軸承的 BPFO 本來就不是嚴格週期，少了抖動，衝擊串會變成一排等距譜線，
純音佔比偵測器會把整串寬頻衝擊算成純音（實測 `tonal_ratio` 會衝到 0.96）。

於是 `target_indicators`（模型）→ `synthesize_waveform`（渲染）→
`indicators_from_waveform`（量回去）形成一個可被測試檢查的閉環。實測回歸誤差：

| 指標 | 誤差 |
|---|---|
| `spl_db` | < 0.01 dB（精確） |
| `high_band_ratio` | < 0.02 |
| `tonal_ratio` | < 0.08（系統性偏低：中值濾波會吸收掉一部分純音能量） |
| `crest_factor_db` | 衝擊性強時精確；低於約 11.4 dB 時render 不下去 —— 那是高斯噪音成分**自身**的波峰因數下限，物理上無法突破 |

這條閉環的意義：**DCASE 驗證用的那個特徵抽取器，可以直接跑在孿生體產生的音訊上**。
`tests/test_acoustics.py` 用它做了一次完全不依賴資料集的端到端測試 ——
在合成的正常音訊上擬合偵測器，再對合成的故障音訊打分，分數必須顯著更高。

### 7.3 聲音怎麼進入診斷排名

融合進既有的「指紋餘弦」項，而不是新開一個加權項：

```
cos_fused = (1 − share) × cos_sensor + share × cos_acoustic
share     = 0.20 × gate                     gate ∈ [0, 1]，由聲學偏離向量長度決定
```

有效權重：**聲音 0.75 × 0.20 = 0.15**、**感測器 0.75 × 0.80 = 0.60**，
歷史先驗 0.15 與文件支持度 0.10 完全不動。

* **為什麼併進去**：新開一個加權項會改掉 0.75 / 0.15 / 0.10 這組已被 Dashboard、
  稽核軌跡與提案書引用的數字，也會讓畫面上「合計 = 各項相加」對不起來。
  融合是加法上封閉的：`cos_fused` 仍是一個 [−1, 1] 的餘弦，整條加權式一個字都不用改，
  而拆解明細（`scores.cosine_sensor` / `scores.cosine_acoustic`）照樣可稽核。
  附帶好處：`signal_strength` 仍只由四個感測器訊號算出，
  「訊號強度閘」與 Orchestrator 的 `confirm_diagnosis` 門檻語意完全不變。
* **為什麼是 0.20 而不是更高**：因為 Demo 的聲音是**推導出來的**，不是量到的。
  讓推導量的權重逼近真正量到的訊號，會製造「兩個獨立來源互相印證」的假象。

### gate 的三段行為

| 聲學偏離量 | gate | 行為 |
|---|---|---|
| < 0.25（死區） | 0 | **完全棄權**，`cos_fused = cos_sensor` |
| 0.25 – 0.60 | 線性 0 → 1 | 部分發言權 |
| > 0.60 | 1 | 完全發言權（`share` = 0.20） |

**死區不是保守，是一條保證。** 四個聲學指標各帶量測雜訊，正規化後每維約 N(0, 0.06)，
四維合成的偏離長度典型值就有 0.12、尾端到 0.25 —— 一台完全健康的機器，
它的麥克風偏離量永遠不會恰好是零。沒有死區的話，健康機台的雜訊會讓 `share`
變成一個小的非零值，「多裝一支麥克風不會動到既有結論」就只是**近似**成立。
設了死區之後，這句話變成可以被測試**逐位元**驗證的性質
（`test_a_quiet_microphone_leaves_the_diagnosis_bit_for_bit_unchanged`）。

### 7.4 接進去之後，既有行為改變了多少

同一個 seed、同一組情境，把 `W_ACOUSTIC_SHARE` 設 0（關聲音）與 0.20（開聲音）各跑一次：

**Benchmark 彙總（guardian 模式，5 情境 × 平均）**

| KPI | 關聲音 | 開聲音 | 變化 |
|---|---:|---:|---|
| 根因診斷正確率 | 100.0% | 100.0% | 不變 |
| 平均診斷時間 | 4.2 min | **4.0 min** | −0.2 min |
| 平均診斷信心度 | 0.74 | **0.75** | +0.01 |
| 產能達成率 | 92.44% | **92.50%** | +0.06 pp |
| 能源浪費 | 0.39 NTD | **0.38 NTD** | −0.01 |
| 碳排浪費 | 0.06 kg | **0.05 kg** | −0.01 |

**Baseline A 與 Baseline B 完全不變**（它們不跑診斷）。

逐情境看，只有 `cooling-failure` 有超出信心度以外的變動：聲音讓它**早一分鐘**確診
（7.0 → 6.0 min），於是產能與能源跟著小幅改善；
該情境的信心度從 0.76 掉到 0.72 不是退步，是因為現在在**訊號更弱的時間點**就下判斷了。
`hazard-zone` 完全不變 —— 沒有設備故障，麥克風落在死區內棄權。

單次診斷（seed 99，注入後第 4 tick 確認）的信心度變化：

| 情境 | 關聲音 | 開聲音 | Δ |
|---|---:|---:|---:|
| bearing-degradation | 0.863 | **0.899** | +0.036 |
| cooling-failure | 0.734 | **0.843** | +0.109 |
| motor-overload | 0.768 | **0.846** | +0.078 |

三個情境的 top-1 根因都沒有改變，只是更有把握 ——
**聲音的作用是把既有的正確答案推得更確定，不是換一個答案。**
