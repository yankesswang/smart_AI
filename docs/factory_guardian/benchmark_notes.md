# Benchmark 方法說明

> 這份文件回答評審最可能追問的三件事：
> **對照組是怎麼定義的、情境的數字是怎麼注入的、為什麼可以相信這個比較。**
>
> 重跑全部數字：
>
> ```bash
> factory-guardian benchmark --out benchmark.json     # 11 情境 × 4 模式
> pytest -q tests/test_benchmark.py                   # 報表本身的測試
> ```
>
> 程式碼：[`benchmark.py`](../../factory_guardian/benchmark.py)、

> [`twin/scenarios.py`](../../factory_guardian/twin/scenarios.py)、

## 1. 四個對照組的定義

四組跑在**相同亂數種子（20260809）、相同情境、相同總 tick 數**的孿生體上。
差別只有兩件事：**看得到什麼**（偵測器）與**看到之後做什麼**（處置）。

| | 偵測器 | 影像/工安 | 處置 | 重試 |
|---|---|---|---|---|
| **Baseline A**｜固定門檻告警 | 固定門檻，打在**原始瞬時讀值**上，只認 CRITICAL | 無 | 只發告警 | 無 |
| **Baseline B**｜偵測即停機 | 完整偵測器（趨勢 + 健康度 + N-of-M 確認） | 有 | 立刻停機 + 維修，技師零等待 | 無 |
| **Baseline C**｜**現行流程** | 同 A（固定門檻、原始讀值、只認 CRITICAL） | **無** | 告警 → **人工判定根因 90 分鐘**（機台照跑、照劣化）→ 停機維修 → 復機。**不轉單** | 無 |
| **Guardian** | 完整偵測器 | 有 | 八階段閉環：診斷 → 影響 → 規劃 → 安全 → 核准 → 執行 → 驗證 | 有（最多 2 次） |

### 1.1 為什麼 Baseline C 才是該比的對象

A 和 B 都是**理想化的極端**：

* A ＝ 告警**完全沒被接住**。沒有工廠是這樣的 —— 有人會看告警。
* B ＝ 告警**完全被接住**，而且技師零等待、零判斷時間。也沒有工廠是這樣的。

拿 A 當「現況」會系統性高估我們的價值，拿 B 當「現況」會低估現行流程。
`41.3% 對 94.6%` 這種開場撐不住第一個追問。

Baseline C 把現行流程真正花時間的那一段放進模擬：**人工判定根因的 90 分鐘**。
這個數字不是我們編的，它就是 [`business_case.md`](business_case.md) §3 假設參數表裡的
「現行流程人工判定根因所需工時 = 90 分鐘（到場 15 ＋ 現場量測 30 ＋ 查手冊與歷史工單 30 ＋
與生產確認 15）」—— ROI 模型和 Benchmark 引用的是同一個數字，兩邊不能各講各的。

> **`business_case.md` §2.1 的「機率混合」照舊有效。** 那一層算 ROI 用的仍然是
> `逃逸率 × A + (1 − 逃逸率) × B`。Baseline C 不是拿來取代它的，
> 它是**第三個各自自洽的真實系統**，讓 Benchmark 表格上有一個現場工程師認得出來的對照組。
> 商業層要不要改用 C，是另一個決定，不在這次改動範圍內。

### 1.2 Baseline C 的三個建模決定（每一個都對現況有利或中性）

1. **90 分鐘期間機台繼續跑、繼續劣化。**
   90 分鐘量的是「判定根因」，不是「反應時間」；現行流程在判定結論出來以前，
   不會停一台還在出貨的機台。這是現況的**悲觀端**（樂觀端是 B）。
2. **判定期間若發生二次損壞（軸承咬死、馬達燒毀），判定立刻結束、直接進維修。**
   故障自己揭曉了，不需要再查手冊。少了這一條，Baseline C 會在一台已經報廢的機器旁邊
   繼續「查手冊」—— 那不是現況，那是稻草人。
   **實測結果：三個設備故障情境的判定流程一次都沒跑完**，平均在第 40 分鐘被打斷。
3. **維修工時取自實際故障的 `repair_min`，也就是說 Baseline C 的判定永遠是對的。**
   人到現場把機器拆開來看，最後總會找到真正壞的是什麼。這個假設對現況**有利**，
   比較結果因此是保守的。（Baseline C 不是 Agent，它是評分用的流程模型，
   所以讀取實際故障不違反「Agent 看不到答案」那條紅線。）

### 1.3 為什麼 Baseline C 沒有攝影機

現行流程的工安控制是**程序性**的（SOP、圍籬、教育訓練、定期巡檢），不是**偵測性**的。
把 AI 攝影機送給對照組，等於假設現況已經有了我們要新增的那個能力。
所以 `hazard-zone` 情境裡 C 和 A 一樣：**88 分鐘曝露**。

## 2. 情境三族與注入參數

情境定義在 [`twin/scenarios.py`](../../factory_guardian/twin/scenarios.py)；
`FieldScenario` 額外帶兩樣孿生體內部設定：`disturbances`（干擾）與 `reality_gap`（現實落差）。
兩者都不會進入任何 Agent 的輸入，`snapshot()` 也不會輸出它們
（測試：`test_twin.py::test_snapshot_never_exposes_disturbances_or_reality_gap`）。

### 2.1 設備故障情境（4 個，徵兆照手冊走）

| 情境 | 注入 | 視野 |
|---|---|---|
| `bearing-degradation` | `bearing_degradation` @ M-A，t=2，ramp 10 | 110 tick |
| `cooling-failure` | `cooling_failure` @ M-A，t=2，ramp 8 | 110 |
| `motor-overload` | `motor_overload` @ M-A，t=2，ramp 9 | 110 |
| `bearing-with-intrusion` | 軸承劣化 @ t=2 ＋ 人員闖入 @ t=6 | 110 |

### 2.2 無故障干擾情境（4 個，Ground Truth 為空）

沒有這一族，False Positive 那格 KPI 永遠是空的 —— 不是零誤報，是沒有機會誤報。
四個都跑 75 tick，機台**完全沒有故障標籤**。

| 情境 | 注入（相對名目值的偏移） | 形狀 | 只動讀值？ |
|---|---|---|---|
| `fp-sensor-spike` | vibration **+6.8**（t=12）、**+6.2**（t=34） | 各 1 個 tick | **是**（`sensor_only`，機台物理完全沒動） |
| `fp-restart-transient` | current **+6.0**、vibration **+3.0**、rpm **−12**、temp **−3**（t=14） | 1 tick 後衰減 | 否（真的發生的啟動暫態） |
| `fp-load-step` | current **+4.2**、temp **+7.0**、vibration **+0.5**、rpm **−1.0**（t=16） | ramp 3 tick 後**維持到結束** | 否 |
| `fp-warm-up` | temperature **+26.0**（t=10） | ramp 4 → hold 3 → 8 tick 衰減到殘留 42% | 否 |

**幅度是怎麼選的**：讓「固定門檻」這個判準真的會踩線。
`fp-sensor-spike` 的 9.2 mm/s、`fp-restart-transient` 的 15.0 A、`fp-load-step` 的 14.4 A、
`fp-warm-up` 的 85.5 °C，都超過該訊號的 CRITICAL 門檻。
如果幅度小到誰都不會報，這一族量到的就只是「沒事發生」，不是誤報率。

> **一個必須講清楚的邊界**：`fp-warm-up` 的峰值確實踩進危險帶，而且持續上升 8 分鐘。
> 在那個當下，它和早期冷卻失效**沒有任何可觀測的差別**。
> 這一族量的是「可分辨的干擾上，系統會不會過度反應」，
> 不是「系統能不能分辨物理上分不開的東西」。後者沒有人做得到。

### 2.3 現實落差情境（2 個）

用來拆掉一個循環論證：Diagnosis Agent 比對的手冊指紋（`fault_signatures()`）
和 Simulator 生成訊號用的 `FaultModel.deltas` 是**同一組數字**。
手冊怎麼寫、機台就怎麼壞 —— 診斷正確率 100% 因此是同義反覆，不是量測。

| 情境 | 真實故障 | 落差 | 理由（現場說得通的版本） |
|---|---|---|---|
| `bearing-atypical` | `bearing_degradation` | 指紋倍率 vibration **×0.15**、temperature **×1.60**、current ×0.90、rpm ×0.60；劣化速度 **×1.8** | 這台去年換過主軸座與避震座，振動被吸收掉大半；潤滑脂配方不同使溫升更明顯 |
| `cooling-with-stuck-vibration` | `cooling_failure` | vibration 感測器**卡在 3.8 mm/s**（警戒帶之下，不會自己告警） | 感測器卡在一個曾經合理的數字上 —— 這正是卡值最難發現的地方 |

三條紅線在這裡一樣成立：

* 落差只改變 Simulator 內部狀態或**感測器回報值**，不產生任何給 Agent 的標籤。
* `fork_as_belief()` 把落差**全部清掉**：規劃永遠跑在**手冊物理**上，因為 Agent 只知道手冊
  （測試：`test_twin.py::test_belief_model_drops_every_reality_gap`）。
* 感測器故障只動回報值，不動 `clean_signals` —— 一支壞掉的感測器不會讓機台真的少做幾件。

## 3. 為了誠實而改動的偵測與處置邏輯

這三項都會**降低** Guardian 的帳面數字，寫在這裡是因為它們必須被追問得起。

### 3.1 門檻確認（N-of-M）：越界要在最近 3 個取樣裡出現 2 次

`MonitoringAgent.confirmed_bands()`，只作用在 `full` 模式（Baseline A / C 維持原始瞬時讀值 ——
那正是「固定門檻告警」這個對照組的定義）。

* **為什麼**：接點抖動、電磁干擾、啟動突波都會讓單一取樣跳過危險門檻，而機台完全沒事。
  這是 DCS/SCADA 常見的 N-of-M 去彈跳，不是我們發明的東西。
* **代價**：真實故障的偵測晚**至多 1 個 tick**（要等第二個越界取樣）。
* **為什麼不用平滑值判帶**：加權平均會被一個尖峰拉高好幾個 tick（尖峰退出視窗才會消失），
  反而讓一次干擾變成一串告警。

同一條規則延伸到工安偵測器：`SR-02`（振動超標）、`SR-03`（高溫）讀的是和 Monitoring Agent
**同一支感測器**，所以它們也要通過確認才會觸發閉環。人員類規則（`SR-01` 闖入、`SR-04` 煙霧、
`SR-05` 跌倒、`SR-08` 護具）不受影響 —— 那是影像直接看到的事實，一格畫面就該停。
**任何工安裁決（`review_plan` / `gate_execution`）都沒有被放寬。**

### 3.2 動設備前的觀察窗：6 個 tick

`Orchestrator.confirm_diagnosis(require_observation=True)`，等於 `MonitoringAgent.WINDOW`。

* **為什麼是一個完整視窗**：要分辨「訊號跳到新穩態」（換規格、暖機、重啟）和
  「才剛開始的劣化」，唯一的方法是看它**還動不動**。而視窗裡只要還留著那個階躍的邊緣，
  兩者在數學上就是同一條線。這幾分鐘不是保守，是**資訊還不存在**。
* **代價（實測，把 `observe_ticks` 設成 0 再跑一次同樣三個情境）**：
  MTTD **5.0 → 10.7 分鐘**，產能達成率 **96.9% → 94.6%**（少 2.3 個百分點）。
* **收益**：`fp-load-step` 從「停機」變成「只告警」；`bearing-atypical` 的錯誤初次診斷
  被糾正回正確答案。
* **工安事件不受這條限制**：人已經站在運轉中的機台旁邊，那不是一個需要多看幾分鐘的趨勢。

### 3.3 自我節制：兩種情況下閉環主動放棄處置

`Orchestrator._abstain_reason()`。兩個判準都只讀 Agent 看得到的東西：

1. 診斷自己說**沒有設備故障徵兆**（`no_equipment_fault`，偏離量還在正常區間內）。
2. 異常**已經停在一個新的穩態**（一個完整視窗內健康度掉不到 3 分、且最壞趨勢低於門檻）。

兩者都只在**沒有現場工安風險**時成立 —— 人在危險區裡的時候，「再看看」不是一個選項。
**棄權不等於不理會**：告警照發、監控照跑，只是不改變任何設備狀態。

### 3.4 兩個孿生體層面的修正

* **降速工作點跟著 `factor` 走**（`_act_derate`）。先前 `factor` 被收下來卻沒有使用，
  於是「降到四成」和「降到八成」跑出完全一樣的結果，方案掃描少了一個真正的維度。
  現在 load / rpm / 故障表現壓抑係數都以預設工作點（0.60）為基準等比縮放；
  沒給 `factor` 時行為**逐位元不變**（測試守著）。
* **維修工時不足就修不好**（`_finish_maintenance`）。工單上的工時是依**診斷結果**開出來的
  （冷卻 30 分、軸承 40 分、馬達 55 分）。診斷錯了，技師就會帶著錯的零件、排著不夠的工時進場，
  時間到了把機台交回，故障其實只被處理掉一部分。
  少了這一段，「診斷錯」在模擬裡完全沒有代價 —— 因為不管開什麼工單，維修都會把故障清成 `None`。

## 4. KPI 的定義（容易被誤讀的幾個）

| KPI | 定義 | 為什麼這樣定義 |
|---|---|---|
| `first_diagnosis_correct` | **偵測當下**第一次指紋比對的結果 | 它和「確認之後」可能不是同一個答案，而那個差距就是觀察窗買到的東西 |
| `diagnosis_correct` | **最終**（確認、必要時重規劃之後）的結果 | 系統交出去的答案是這一個 |
| `false_positive_events` | 在**沒有故障的機台**上發生的告警**事故**，一台機台算一次 | 逐條數告警訊息會因為「Guardian 有 WARNING/CRITICAL 兩級」而罰它，那量到的是告警設計不是誤報 |
| `false_positive_actions` | 在 Ground Truth 為空的情境裡，成功執行的停機／降速／維修／轉單次數 | 誤報的成本不在告警，在誤動作。工安情境不算（停機正是那裡的正解） |
| `time_to_diagnose_min` | 偵測 → 可據以行動的診斷，含刻意等待 | Baseline C 是「判定流程實際花掉的時間」，被二次損壞打斷就以打斷點計 |
| `replan_recovery_min` | 從「驗證失敗」到「驗證通過」的模擬分鐘數 | 沒失敗過或失敗後再也沒通過就是 `—`，不要用 0 假裝它很快 |
| `production_attainment_pct` | 實際產出 ÷ **事故前**名目產能 | 分母固定在事故前的計畫值，轉單提高備援機台負載時可能超過 100% |

彙總分三族（`aggregate_by_family`）：**設備故障 / 無故障干擾 / 現實落差**。
混在一起平均，誤報率會被有故障的情境稀釋、產能會被沒事發生的情境拉高，兩個數字都失去意義。
`aggregate`（全情境）這個鍵維持原樣，因為商業案例層讀的是它。

## 5. 目前做不到的事

寫在這裡，是因為它們在 Benchmark 表上看起來像是「已經做到」。

1. **「驗證失敗 → 重新規劃」沒有在任何情境上發生。**
   重規劃次數目前全部是 0。原因不是重試壞掉，而是在這些落差下方案排名仍然選中
   「轉單 + 停機維修」，而停機維修對診斷錯誤是**容錯**的 —— 機台停下來就不會再劣化。
   要讓這條路徑自然出現，需要一個「排名會選擇讓機台繼續運轉」的落差情境，
   那牽涉到 `optimizer.py` 與 `agents/production.py`，不在這次改動範圍內。
   重試邏輯與它的兩個 KPI 目前由 `test_orchestrator.py` 直接注入一次驗證失敗來守住。
2. **一個 Episode 只計分一次事故**（`MAX_RESPONSES = 1`）。
   復發偵測的機制已經備好（告警狀態 acknowledge、復機暫態 grace），
   但「一次事故該被計分幾次」是另一個問題：混在同一張表裡，
   讀表的人會分不清楚產能差異來自處置品質還是來自事故次數。
3. **`fp-warm-up` 上 Guardian 誤動作 3 次**（轉單 + 停機 + 維修）。
   要分辨它需要把觀察窗從 6 分鐘拉到 10 分鐘，而那 4 分鐘對真實故障是有代價的。
   我們選了 6 分鐘，代價與收益都在表上。
