Why it is different

和「會發告警的系統」差在哪三件事

傳統系統停在「哪裡有問題」，後面的原因、影響、方案、風險、結果，全部靠人跨系統拼。這裡把那段接起來，而且每一步都留下可稽核的紀錄。

POINT 01

不是給建議，是把處置做完並負責

從偵測到驗證是一條完整的閉環：找出根因、算出哪幾張訂單會遲、把可行做法一個一個在數位孿生裡試跑，再送進核准與執行。

一次事故產出 4 種候選方案，每種都先乾跑 30 分鐘看結果
POINT 02

會動到設備的事，一定要人簽名

停機、降速、進維修屬於高風險動作，系統永遠只能「建議」，不能自己按下去。安全硬規則優先於方案分數 —— 分數再高，被擋就是出局。

「關閉安全保護」是 forbidden：沒有任何人或模型能核准
POINT 03

做完會量測，而不是相信自己的預測

執行後在孿生體上再跑 30 分鐘，用實際量到的數字檢查兩件事：有沒有達到當初的預測，以及有沒有贏過「什麼都不做」。

全部檢查通過才算 PASS；失敗最多重試 2 次後升級人工
The seven steps

七個步驟，六個 Agent 各守一段

每個 Agent 只做一件事，而且輸出是結構化的資料，不是一段話 —— 下一個 Agent 才接得住。以下每一步都寫明：它看到什麼、它怎麼判斷、它交出什麼。

  1. 01

    發現異常

    DetectMonitoring Agent

    機台的振動、溫度、電流每分鐘都在被看。重點是不只看有沒有超過紅線，也看它是不是正在往紅線走 —— 這是能提早處理的關鍵。

    看到什麼每台機台的感測讀值，以及上下游機台的依賴關係
    怎麼判斷固定門檻、趨勢斜率、健康度衰減，三者任一成立就開事件
    交出什麼一筆異常事件：哪台機、哪個訊號、WARNING 還是 CRITICAL

    同時還有另一雙眼睛：Safety Agent 在看現場影像。人員站進運轉中的危險區時，不必等設備先壞，直接觸發事件。

  2. 02

    確認原因（證據不夠就先不動手）

    DiagnoseDiagnosis Agent

    剛觸發告警時訊號還很微弱，這時候就去停機是不負責任的。所以系統會先繼續看幾分鐘、累積證據，等到有把握才往下走。

    看到什麼各訊號的偏離量、維修手冊裡的故障指紋、該機台的歷史故障率
    怎麼判斷指紋相似度佔 75%（含聲音指紋）、歷史先驗 15%、文件檢索 10%
    交出什麼根因排名 + 信心度，每一項都附證據來源（哪個訊號、哪條 SOP）

    硬規則：信心度低於 65% 就繼續觀察，最多等 10 分鐘；這段期間不執行任何設備動作，等待理由會寫進稽核軌跡。

  3. 03

    算出這件事會賠多少

    ImpactProduction Agent

    把「機台有問題」翻譯成廠長聽得懂的話：哪幾張訂單會遲、遲多久、少做幾件。沒有這一步，後面就沒辦法比較哪個方案划算。

    看到什麼MES 訂單與交期、產線節拍、下游機台會不會因此斷料
    怎麼判斷以目前劣化速率往前推算，得到產能損失與訂單延遲
    交出什麼受影響訂單清單、最大交期延遲（分鐘）、預估產能損失（件）
  4. 04

    把四種做法都先跑一次模擬

    Plan / Dry-runProduction Agent

    這裡不是問 AI「你覺得該怎麼辦」，而是把每個做法都丟進數位孿生跑 30 分鐘，看它實際會把產線帶到哪裡，再用固定公式排名。

    候選方案A 維持全速｜B 降速延後維修｜C 立即停機維修｜D 轉單到備援機台
    怎麼排名六個準則加權：安全 30%、交期 22%、產能 20%、復原 12%、成本 8%、設備保全 8%
    交出什麼排名 + 每個準則各貢獻多少分，所以看得出「為什麼是這一案」

    紅線：排名是純計算，LLM 不參與。所有輸入（產能、交期、復原時間、成本、殘餘風險）都來自模擬乾跑的結果，不是估的。

  5. 05

    安全與權限把關

    Safety & PolicySafety Agent

    分數最高不代表可以做。方案要先過兩關：安全硬規則（這樣做會不會出事）和權限規則（這個動作誰有資格決定）。

    看到什麼方案的模擬軌跡、現場影像、機台狀態、SOP 條文
    怎麼判斷規則逐條檢查，任一條觸發 BLOCK 就是硬限制，直接出局
    交出什麼裁決 ALLOW／APPROVAL／BLOCK ＋ 觸發的規則編號與 SOP 依據

    舉例：影像判定人員還在危險區，而某方案讓機台繼續運轉 —— 不管它的產能分數多高，一律 BLOCK。

  6. 06

    執行（下指令前再檢查一次）

    ExecuteMaintenance Agent

    取得核准之後，動作才真的下到設備，同時開出維修工單。下指令的前一刻會重跑一次安全閘門 —— 因為從核准到執行之間，現場可能已經變了。

    看到什麼核准紀錄（誰簽的、理由、逾時就不執行）＋ 執行當下的最新現場狀態
    怎麼判斷執行前安全閘門沒過就中止，不會硬做
    交出什麼每個動作的實際效果、維修工單編號、完整稽核紀錄
  7. 07

    回頭量測，沒效就不算完

    VerifyVerification Agent

    執行後再跑 30 分鐘，用實際量到的數字檢查，而不是相信當初的預測。它同時回答兩個問題：預測準不準？以及，有做真的比沒做好嗎？

    比什麼（一）實際產線達成率 ≥ 方案預測（容忍 12%）、實際延遲 ≤ 預測（容忍 15 分鐘）
    比什麼（二）贏過「什麼都不做」這個反事實基準；機台健康度沒有再往下掉
    交出什麼PASS／FAIL ＋ 每項檢查的預測值對實際值，全部通過才算 PASS

    為什麼不是跟「執行前」比：設備劣化是進行式的，拿 30 分鐘後的結果去比事故剛發生的當下，任何方案都必然「變差」，那個比較沒有意義。

FAIL → RETRY

回饋路徑不是回到第 04 步拿舊清單的第二名 —— 第一個方案已經改變了工廠狀態，那份清單的預測全都過期了。所以是從當下的狀態重新診斷、重估影響、重新排名。

Who decides what

哪些動作系統可以自己做，哪些一定要人

✓LLM 可以做的事

  • 把散在各處的證據整理成人看得懂的脈絡
  • 解釋這個排名為什麼是這樣、風險在哪
  • 寫交班摘要與稽核敘述

用途是讓人快速看懂發生什麼事 —— 它是解釋者。

✕LLM 不能做的事

  • 更動任何一個分數或方案排名
  • 決定 ALLOW / APPROVAL / BLOCK
  • 直接對設備下指令，或覆寫 Safety 的判定

就算 LLM 完全離線，控制路徑照樣跑得完；少的只有敘述。

Safety verdicts

安全把關只有三種結果

每個候選方案都會拿到其中一種裁決。這三種結果決定它能不能往下走，而且優先於方案分數。

補充：需要人核准，代表的是「這件事該有人負責」這個治理程序，不代表這個方案比較危險。真正的危險由 BLOCK 表達，而 BLOCK 是硬限制。

Glossary

頁面上的名詞，一句話解釋

快照 Snapshot

Agent 唯一看得到的工廠狀態。裡面不含正確答案 —— 模擬器知道真正的故障是什麼，但不會告訴 Agent，否則診斷能力就是假的。

乾跑 Dry-run

在數位孿生裡先把一個方案跑 30 分鐘，看它會把產線帶到什麼結果，再決定要不要真的執行。

信心度 Confidence

觀測到的異常樣態和手冊裡故障指紋的吻合程度，0 到 1。低於 0.65 系統就不動設備。

故障指紋 Fault signature

某種故障會在各個訊號上留下的特定形狀，例如軸承劣化＝振動先漲、溫度慢漲、電流微升。比對的就是這個形狀，不是單一數值。

政策引擎 Policy Engine

寫死的權限規則表，決定一個動作可以自動、需要核准、還是永遠禁止。它是規則，不是模型。

反事實基準 Counterfactual

「如果什麼都不做會怎樣」。用它來證明系統的介入真的有價值，而不只是「事後看起來還行」。

稽核軌跡 Audit trail

每一次判斷、裁決、核准、執行與驗證的完整紀錄，包含依據與時間，事後可以逐筆追查。

數位孿生 Digital Twin

工廠的模擬體，同時扮演兩個角色：讓方案先在裡面試跑，以及在執行後提供真實量測結果供驗證。
